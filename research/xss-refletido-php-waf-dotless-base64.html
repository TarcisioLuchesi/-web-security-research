CVE-2026-61957 — Reflected XSS in miniOrange OTP Verification: PHP and dotless payloads

Investigating GET parameter-name reflection in HTML and Base64 encoding to avoid characters transformed by PHP parameter parsing.

08 nov 2026 · write-upCVE-2026-61957PHPWordPressCWE-79CVSS 7.1
Por Tarcísio Luchesi (Poystick)Write-up: AI-Assisted CVE publicada em 27 jul 2026

During my research on the miniOrange OTP Verification WordPress plugin, I found an interesting behavior: GET parameter names were reflected into the HTML response. When those names are printed into markup without contextual escaping, they can also become an entry point for reflected XSS.

What made this investigation interesting was the path between the browser and PHP. I needed to understand what happens to payload characters when they are used as parameter names, not parameter values.

Identification and responsible disclosure

The vulnerability I reported was assigned CVE-2026-61957. Patchstack credits me as Tarcísio Luchesi (Poystick), with a report date of June 12, 2026 and publication on July 27, 2026. It affects miniOrange OTP Verification through version 5.5.1 and was fixed in 5.5.2.

The published classification is CWE-79, unauthenticated reflected XSS, with a CVSS 3.1 score of 7.1 (High) and victim interaction required. The detailed analysis here is my technical interpretation; consult the Patchstack vulnerability database and CVE records for the original record.

The entry point: a GET parameter name

In typical XSS tests, we control a value such as ?q=test. Here the hypothesis was that a key could reach HTML without contextual encoding. Inspecting only $_GET['q'] would not be sufficient: the application might retrieve and display the keys themselves.

GET /pagina-de-teste?chave_controlada=1 HTTP/1.1
Host: laboratorio.example

Whenever a user-controlled key appears in HTML, check its actual output context: text, attribute, JavaScript, or another context. That determines whether the reflection is dangerous and which output encoding is needed.

The obstacle: PHP parameter-name normalization

PHP interprets names of external parameters in a particular way. Dots and spaces can become underscores; square brackets also influence array syntax and key parsing.

// Exemplo conceitual de interpretação de chaves:
?nome.campo=1     → nome_campo
?nome%20campo=1   → nome_campo

For example, JavaScript that relies on document.cookie may be altered if the dot is normalized while used as a parameter name. The browser may receive a different JavaScript expression from the one originally sent. This must be checked against the actual HTML response: some applications reflect the raw query string instead of normalized PHP keys.

My approach: a dotless encoded payload

I explored keeping the original JavaScript expression encoded as Base64, then reconstructing it in the browser with atob() and the Function constructor. This avoids placing a dot-sensitive expression directly into the GET parameter name.

Controlled parameter name → PHP parsing and key normalization → unescaped HTML reflection → browser JavaScript → atob() decoding → Function() reconstruction → execution in the page context

Simplified PoC explaining the technique

The following self-contained example is suitable for a console or local test. It demonstrates the mechanism without publishing a session-collection routine:

Function(atob('YWxlcnQoMSk'))()

The decoded string represents:

alert(1)

The Base64 sample omits final = padding, which atob() accepts in this case. This does not mean that every such payload works in every application. It illustrates why encoding can avoid particular characters in the input representation.

Evidence note: The original report describes a proof of concept involving a network request and access to document.cookie. This publication replaces the exfiltration routine with a local demonstration and does not include session data, a real test target, or webhook identifiers.

Why can this affect pattern-based filters?

A filter that looks only for literal JavaScript signatures may not recognize the same content after encoding. Similar reasoning applies to WAF rules relying on isolated characters or signatures. But a differently shaped payload is not proof of a universal WAF bypass. To claim bypass of a specific rule, compare the blocked original, accepted variation, and actual browser execution in the same authorized environment.

Impact and limitations

Exploitable reflected XSS can allow JavaScript to run in the application's origin when a victim opens a crafted URL. This could enable unauthorized interactions or access to origin data exposed to JavaScript. However, HttpOnly cookies are not readable through document.cookie, and reading a cookie is not itself proof of account takeover.

Any claim of account compromise requires additional evidence about session behavior and exploit context. If the reflection occurs on an administrative screen, its reach also depends on access requirements, URL handling, CSP, and other defenses.

How to fix it

Prevent controlled parameter names from being interpreted as HTML or JavaScript at the output. In WordPress, use esc_html() for HTML text, esc_attr() for attributes, esc_url() for URLs, and explicit allowlisting of expected parameter names rather than reflecting arbitrary keys.

// Exemplo para exibição de texto HTML em WordPress
echo esc_html($nome_do_parametro);

A restrictive Content Security Policy can provide defense in depth, but does not replace contextual escaping and application-level validation.

What I learned

A parameter name can be an attack surface. Instead of changing payloads randomly when a traditional expression failed, I traced how PHP transformed the input, identified which characters were lost, and investigated ways to preserve its intended meaning until browser execution. Understanding the parser, representation, and output context was more useful than memorizing signatures.
