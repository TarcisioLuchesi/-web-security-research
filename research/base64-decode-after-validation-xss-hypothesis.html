Base64, early validation, and XSS: when input changes after filtering

Research into whether validating encoded input before decoding can allow unsafe HTML to reach an output sink.

Nov 20, 2026XSSBase64Source-to-sinkAI-AssistedNot verified in a real-world target
Hypothesis proposed by Tarcísio Luchesi (Poystick)
Research status: This is a technically plausible mechanism already described in security literature, not proof of exploitation in Gmail, Google, or any particular real-world application. No new vulnerability class is claimed.

1. The hypothesis

An application might validate a Base64 string, store or transmit it, and later decode it for display. If validation covers only the encoded representation and the decoded text reaches an HTML interpreter without adequate protection, XSS may become possible. The issue is not Base64 itself, but the order of operations and the trust boundary between input, decoding, and output.

Untrusted input → Base64 → encoded-input validation → storage / transit → Base64 decode → unsafe HTML output → potential XSS

2. Base64 without padding

Some decoders accept Base64 without final = padding. This does not change the decoded bytes and is not a bypass by itself; acceptance depends on the decoder.

A harmless representation example:

Entrada original: <b>teste</b>
Base64 sem padding: PGI+dGVzdGU8L2I+
Resultado decodificado: <b>teste</b>

Data that is safe when displayed as text can become dangerous if interpreted as active HTML.

3. Validation is not necessarily sanitization

A regular expression allowing letters, marks, symbols, numbers, and punctuation does not automatically reject HTML markup. For example, the Amazon Cognito username character pattern [\p{L}\p{M}\p{S}\p{N}\p{P}]+ is not an XSS defense. Passing username validation says nothing about downstream rendering. A complete bypass requires proving the actual data flow across relevant backend and frontend protections.

4. Local PoC: safe and unsafe sinks

This self-contained example uses harmless bold markup rather than JavaScript. It demonstrates the difference between rendering characters as text and interpreting them as HTML.

<div id="seguro"></div>
<div id="inseguro"></div>
<script>
  const encoded = "PGI+dGVzdGU8L2I+";
  const decoded = atob(encoded);

  // Exibe como texto: não interpreta tags HTML.
  document.querySelector("#seguro").textContent = decoded;

  // Interpreta HTML: NÃO utilizar com entrada não confiável.
  document.querySelector("#inseguro").innerHTML = decoded;
</script>

The safe element displays <b>test</b> literally; the unsafe element renders the word in bold. This establishes a change of interpretation, not necessarily script execution.

5. Practical lab scenario: backend accepts Base64, frontend interprets HTML

Imagine an isolated test application that accepts an encoded message, validates only the Base64 characters, and later decodes the value into an unsafe HTML sink. The following lab-only demonstration uses alert(1) as an execution marker; it does not involve a real service.

Step 1 — create and encode the input

Original: <img src=x onerror=alert(1)>
Base64 sem padding: PGltZyBzcmM9eCBvbmVycm9yPWFsZXJ0KDEpPg

Step 2 — validate only the encoded representation

const regex = /^[A-Za-z0-9+/]+$/;
function salvarMensagem(valor) {
  if (!regex.test(valor)) throw new Error("Entrada inválida");
  return valor;
}

That check permits Base64 characters but never inspects the decoded content. It is not a defense against XSS.

Step 3 — decode and use an unsafe frontend sink

<div id="resultado"></div>
<script>
  const mensagem = "PGltZyBzcmM9eCBvbmVycm9yPWFsZXJ0KDEpPg";
  const decoded = atob(mensagem);
  document.getElementById("resultado").innerHTML = decoded;
</script>

In a controlled page without a CSP blocking inline handlers, the invalid image triggers its error handler. This demonstrates a deliberately vulnerable lab flow, not a bypass in an actual product.

Step 4 — fix the output sink

document.getElementById("resultado").textContent = decoded;

textContent displays decoded markup as text. If an application must render third-party HTML, apply an appropriate sanitizer after decoding and before inserting it into the DOM.

6. What evidence would confirm the issue in a real application?

  1. Identify the controllable source, such as a parameter, attribute, API response, or stored message.
  2. Show that encoded input passes the relevant validation and reaches the component under investigation.
  3. Record where decoding takes place relative to validation or sanitization.
  4. Find the final sink — for example, textContent, innerHTML, a template, an attribute, or a URL.
  5. Determine whether the decoded output receives context-specific protection.
  6. Reproduce a security impact in a local or expressly authorized test, correctly distinguishing DOM, reflected, and stored XSS.

7. What about Gmail?

There is no evidence here of a Gmail protection bypass. Email services may have several parsing and sanitization stages, content policies, and isolation. A claim about Gmail would require an actual controllable input/output flow, evidence of operation order, and authorized reproduction. Until then, this remains a general hypothesis, not a Google vulnerability finding.

8. Recommended controls

Treat decoded Base64 as untrusted input. Validate semantics after relevant transformations, use output encoding appropriate to each context, and prefer textContent for text. Sanitize third-party HTML after decoding. Neither encoding, regex checks, a WAF, nor frontend-only checks replace sink-level protection.

9. Conclusion and confidence

The data-flow hypothesis is valid in principle. Encoding can conceal the original representation from superficial checks, but it cannot bypass sanitization properly applied to the decoded value before the sink. The underlying categories — canonicalization issues, post-validation transformations, and XSS — are already known. Confidence is high for technical plausibility and unestablished for any concrete Gmail bypass.
