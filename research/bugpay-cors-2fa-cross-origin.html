Permissive CORS in BugPay's 2FA flow

Cross-origin response reading, impact limitations, a retest restricting origins, and the responsible disclosure outcome.

Nov 6–18, 2026 BugPay CORS 2FA Black-box Severity: Low
Research: Tarcísio Luchesi (Poystick) Report accepted and closed Publication authorized Nov 18, 2026

During a security assessment of BugPay, I investigated a function used to start a two-factor authentication (2FA) challenge. Initially, a page on another origin could call the endpoint and read its JSON response in browser JavaScript. This mattered because the endpoint was part of an authentication workflow — but reading a challenge response is not the same as obtaining an authenticated session.

Outcome: I observed Access-Control-Allow-Origin: * and cross-origin reading of the action: "start" response. On retest, the browser blocked reading from an external origin. BugPay accepted and closed the report, set the final severity to Low, and authorized publication on November 18, 2026.

1. What CORS controls

Cross-Origin Resource Sharing tells the browser which origins may read a cross-origin response. The wildcard * permits non-credentialed cross-origin response reads. It is not automatically a serious vulnerability: public APIs may legitimately allow it. Browsers do not expose credentialed responses to scripts when the server uses the wildcard, so the header alone does not prove that session cookies, protected tokens, or private authenticated content were accessible.

2. The investigated surface

The request used POST /functions/v1/password-login-2fa with the start action to initiate a 2FA challenge. My proof of concept ran in a controlled external origin and checked that JavaScript could read the response body, not merely that the network panel displayed an HTTP 200 or a successful preflight.

External-origin page → browser fetch → POST /functions/v1/password-login-2fa → action: "start" → 2FA challenge → JSON response → external JavaScript (initial test)

3. Initial evidence — November 6, 2026

The initial response had HTTP 200 and a permissive CORS header. The following example is reduced and sanitized rather than a verbatim reproduction:

HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
Content-Type: application/json

{
  "success": true,
  "challenge_id": "[valor omitido]",
  "user_id": "[valor omitido]",
  "email": "[endereço mascarado]"
}

Browser JavaScript from the test origin read the returned JSON and the start action generated a challenge. Identifiers, tokens, codes, and personal data have been removed from this article. The demonstrated finding was cross-origin reading of the initial 2FA operation's response.

4. What the PoC did not establish

  • No demonstrated account takeover: the test did not establish unauthorized access to someone else's account or an authenticated session.
  • No demonstrated access-token exfiltration: the readable start-response fields were not proof of a leaked session token.
  • No complete 2FA bypass: a later verification attempt used a different authentication context and mismatched identifiers.
  • No proven authenticated response read: wildcard access for a non-credentialed response is not evidence that a cookie-protected response was readable.

Some authentication systems intentionally allow a challenge to start before login. Higher-impact conclusions would require proving a separate unintended consequence.

5. Retest — November 9, 2026

After reporting, I reran the external-origin browser test. The endpoint now advertised a specific allowed origin:

Access-Control-Allow-Origin: https://app.bugpay.com.br

The external test origin could no longer read the JSON; the browser blocked access and the PoC reported Failed to fetch. This shows a meaningful CORS change for that tested behavior, not a complete audit or proof that all other 2FA issues were fixed.

6. Coordinated disclosure and BugPay's response

  • November 6: initial cross-origin reading observed at password-login-2fa.
  • November 9: BugPay confirmed the reported configuration and moved the report through review and retest; severity changed from High to Low.
  • November 9: retest showed restricted origins and blocked external response reading.
  • November 18: the report was closed and BugPay explicitly authorized publication.

Acknowledging this behavior is not the same as confirming account takeover. The final Low classification reflects the limited demonstrated impact.

7. Lessons and defensive controls

Evaluate CORS alongside response contents, authentication context, and side effects. Check whether an external script can actually read the response, whether credentials are involved, whether the returned fields are sensitive, and whether a harmful outcome is reproducible. Restrict trusted frontend origins when appropriate, and enforce server-side authorization, abuse controls, 2FA challenge validation, and CSRF protection as relevant. CORS neither replaces authorization nor provides general CSRF protection.

8. Conclusion

The original hypothesis was confirmed only as cross-origin reading of the initial 2FA challenge response. The retest showed that this read was blocked by origin restrictions. The report was accepted and completed at Low severity with publication approval; this account does not claim demonstrated ATO, token theft, or a full 2FA bypass.
