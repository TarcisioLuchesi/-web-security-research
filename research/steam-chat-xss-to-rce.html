From XSS to RCE in Steam Chat

An educational analysis of a chain involving React, BBCode, OEmbed, CEF, custom URI handlers, privilege boundaries, and native execution.

The important insight is that there was no single input → system() → RCE bug. Impact came from chaining smaller capabilities: controllable input, link transformation, special protocols, an embedded browser, and a privileged bridge able to reach the operating system.

Controlled input → React / BBCode / OEmbed → controllable URL → CEF → custom URI → Steam Web Helper → privileged native operation → Windows → RCE

1. Understanding the architecture

Steam Chat ran a web interface inside the desktop client using a customized Chrome Embedded Framework (CEF). The React UI communicated with native Steam components through mechanisms including postMessage, a local WebSocket, and internal interfaces. JavaScript inside CEF should not automatically enjoy the privileges of the native application. The researcher therefore sought a bridge between those contexts.

2. Why React reduced trivial XSS

React normally escapes values rendered as text. In JSX, putting a user-controlled username inside braces does not automatically transform tag-like characters into active HTML:

function Profile({ username }) {
    return <div>{username}</div>;
}

The investigator needed to look beyond trivial tag injection because this path is generally handled as text.

3. React does not eliminate XSS

Browser APIs and non-text contexts remain security-sensitive. User-controlled href, document.location, CSS, innerHTML, and dangerouslySetInnerHTML require checks tailored to their semantics.

Controllable href

function Link({ url }) {
    return <a href={url}>Clique aqui</a>;
}

The DOM markup can remain intact while the URL's scheme or destination becomes unsafe.

dangerouslySetInnerHTML

function Message({ html }) {
    return (
        <div dangerouslySetInnerHTML={{ __html: html }} />
    );
}

Here the value is interpreted as HTML rather than text. The same concern applies to direct writes to innerHTML.

document.location

document.location = userInput;

React does not automatically secure navigation APIs; destination and scheme validation remain necessary.

4. BBCode as an intermediate layer

Steam Chat converted BBCode, a lightweight markup language, into links and HTML. For example, a BBCode tag:

[url=https://example.com]Visitar site[/url]

could become a link:

<a href="https://example.com">Visitar site</a>
User input → BBCode → parser → React / HTML → DOM

5. How a similar bug could appear in PHP

The following intentionally simplified PHP parser demonstrates the same type of trust-boundary error:

<?php

function parseBBCode(string $message): string
{
    return preg_replace(
        '/\[url=(.*?)\](.*?)\[\/url\]/i',
        '<a href="$1">$2</a>',
        $message
    );
}

$message = $_POST['message'] ?? '';

echo parseBBCode($message);

The captured value is inserted into the href attribute without semantic URL validation.

6. URI-based XSS

If a parser accepts arbitrary schemes, a crafted URI can become a dangerous link without breaking out of its HTML attribute:

[url=javascript:alert(document.domain)]Clique[/url]

Conceptually, the generated output could look like:

<a href="javascript:alert(document.domain)">Clique</a>

The key capability is to control what an href means, rather than merely injecting a new tag.

7. The primitive: “I control a URL”

A valuable research question is not only “Did I find XSS?” but “What now consumes this URL?” Even if a javascript: path failed in the customized Steam client, URL control could still matter to other components.

8. Custom URI schemes

Desktop applications may register protocols other than https://:

steam://
spotify://
vscode://
myapp://

An embedded browser may hand such URIs to a native handler, crossing the web-to-desktop trust boundary.

9. The steam:// protocol

The researcher inspected Steam-specific URI handlers to learn which native actions the client would perform and with what privileges. This is why control of a URL in a CEF or Electron-style application may have more impact than the same control in a regular web page.

10. OEmbed and embedded content

External links could become rich embedded content through OEmbed metadata or HTML, potentially involving iframes, players, or special components. Such transformations create extra surfaces when external data is rendered using HTML-oriented sinks.

11. Testing postMessage

Because embedded content can execute in another context, one hypothesis was that it might send messages resembling those used by the legitimate application:

window.top.postMessage(
    { action: "algumaAcao" },
    "https://destino-esperado.example"
);

For the specific route tested, the sandbox blocked the required access. This was a protection that worked, not evidence of compromise.

12. Privilege differences are clues

Some windows exposed capabilities unavailable to others. This is a critical research pattern: can input from a lower-privilege context reach a higher-privilege one? Security impact often depends on crossing exactly that boundary.

13. Windows protocol handlers

The investigation continued into how Windows maps URI schemes and file types to native programs and their arguments. Getting a remote input interpreted by an operating-system handler is evidence that the browser boundary has been crossed, even when the first observed action is limited.

14. Path traversal as another primitive

Path resolution by handlers could be influenced with traversal-like sequences. One observed limit was that a target file had to exist beforehand. Rather than treating the partial result as complete RCE, the investigator considered whether another bridge could remove that limitation.

15. The critical discovery in logs

Steam's console revealed that certain external actions mapped internally to a recognizable structure:

steam://openexternalforpid/<PID>/<URI>

Logs exposed the privileged mechanism behind observed behavior and reduced guesswork about accepted protocols.

16. openexternalforpid as a privileged bridge

Controlled target → steam://openexternalforpid/... → Steam Web Helper → native operation → Windows

The significant boundary crossing was from web-originated content into functionality intended to perform privileged native operations.

17. Representing the root cause in PHP

These snippets describe a fictional internal handler to make the trust boundary understandable:

<?php

function handleUri(string $uri): void
{
    $prefix = 'myapp://openexternal/';

    if (!str_starts_with($uri, $prefix)) {
        return;
    }

    $target = substr($uri, strlen($prefix));

    openExternal($target);
}

The essential question is what openExternal() actually allows:

<?php

function openExternal(string $target): void
{
    /*
     * Anti-padrão didático.
     * Entrada não confiável nunca deveria controlar
     * diretamente uma primitive de execução.
     */

    // shell_exec($target);
}

The dangerous line is deliberately commented out. The example is for understanding the root cause rather than providing a functional executor.

18. From web flaw to RCE

The chain was not a single XSS call to cmd.exe. Multiple consumers and context changes were involved:

Attacker input → message → React / BBCode → URL control → custom URI → CEF → Steam Web Helper → privileged function → native process → Windows → RCE

19. Fixing the source

A link parser must validate the URL's meaning and allowed scheme, not merely escape HTML characters:

<?php

function createSafeLink(string $url, string $text): string
{
    $scheme = strtolower(
        (string) parse_url($url, PHP_URL_SCHEME)
    );

    if (!in_array($scheme, ['http', 'https'], true)) {
        return htmlspecialchars(
            $text,
            ENT_QUOTES | ENT_SUBSTITUTE,
            'UTF-8'
        );
    }

    $safeUrl = htmlspecialchars(
        $url,
        ENT_QUOTES | ENT_SUBSTITUTE,
        'UTF-8'
    );

    $safeText = htmlspecialchars(
        $text,
        ENT_QUOTES | ENT_SUBSTITUTE,
        'UTF-8'
    );

    return '<a href="' . $safeUrl . '">' .
           $safeText .
           '</a>';
}

Contextual HTML escaping and semantic URL validation are complementary protections.

20. Hardening the privileged bridge

Native interfaces should expose narrowly defined, authorized actions rather than a generic instruction to open or execute any caller-supplied target:

<?php

$allowedActions = [
    'open_settings',
    'show_profile',
    'open_help'
];

if (!in_array($action, $allowedActions, true)) {
    throw new RuntimeException('Invalid action');
}

Unsafe: execute an arbitrary target. Safer: choose from known, predefined actions.

21. The research mindset

Think in capabilities: what do I control, where does it go, who interprets it next, what transformations occur, is a trust boundary crossed, does the next component have more privileges, and can that primitive be chained with another? The original researcher did not stop at URL control but investigated its consumers and their authority.

22. A mental model

Primitive + Trust boundary + Privilege difference + Chaining = Higher impact

This perspective also applies to Electron, WebViews, browser extensions, and other hybrid web/native applications.

Conclusion

React reduced trivial XSS but did not eliminate dangerous sinks. BBCode and OEmbed introduced transformations. URL control led to custom protocols; a privileged bridge provided access to native behavior. The resulting RCE depended on the full chain, not one isolated mistake.

Key question: “I control something. Who interprets it next, and what can that component do that I cannot?”
